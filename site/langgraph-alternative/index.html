LangGraph / What Sits Around It

LangGraph runs the agent.
Something has to run the rest.

LangGraph is a good agent framework. If you are choosing one, that is not the argument this page is having. The question this page answers is the one that arrives six months later, when the agent works and the things around it — schedules, budgets, retries, an audit trail, someone asking what last Tuesday cost — turn out to be yours to build.

Written for ·· Teams already running LangGraph
Not for ·· Teams choosing their first agent framework
Verified ·· 2026-08-19, primary sources

01 / The boundary

These are not competitors.
They are two halves of one system.

What LangGraph owns

The loop. State across turns, branching on what the model decides, tool calls, human-in-the-loop interrupts, streaming partial results. It is a library you import into a Python process, and it is good at this.

What nobody owns until you build it

Running that process on a schedule. Stopping it when it has spent enough. Retrying the step that failed without replaying the twelve that worked. Keeping a record a compliance officer can read. Answering “what did this cost” without instrumenting it yourself.

Where Sandcastle sits

Around it. A workflow is one YAML file: steps, dependencies, budgets, retries. Every run is recorded and replayable. It calls models directly, and it can call a LangGraph service as an http step — the two compose rather than replace.

02 / What actually bites

The four things teams hit after the agent works.

None of these are LangGraph defects. They are simply outside what a framework is for — which is exactly why they land on you.

You cannot answer what a run cost

Token accounting is not in the framework. Teams reach for LangSmith, which bills per trace — so observability becomes a line item that scales with usage, and the numbers live in someone else's system. Sandcastle records tokens and cost per step in your own database, because it is the same system that ran the step.

Nothing stops a loop that is spending

An agent that retries its way through a bad tool response can burn real money before anyone notices. There is no built-in ceiling; you write the guard. Sandcastle takes budget_limit_usd on the workflow and stops at it.

The data leaves, and you have to prove it did not

Hosted tracing means prompts and outputs go somewhere else. For an EU team answering to the AI Act, “we self-host the agent but ship the traces to a US SaaS” is the awkward half of the sentence. Sandcastle runs on your hardware end to end, and the audit trail stays there with it.

The workflow is not reviewable

A graph assembled in Python is code, and code review shows you a diff of the assembly, not of the behaviour. A YAML workflow diffs as what changed: this step, this model, this budget. That matters more the more people touch it.

03 / When to stay exactly where you are

Cases where this page is the wrong advice.

The comparison page has a section like this too. It is the part worth reading.

The model must choose its own path

If the sequence genuinely cannot be written down — the agent decides at runtime what to do next, and that is the point — a declarative workflow is the wrong shape. Keep LangGraph. Sandcastle's agent step delegates to a model, but the workflow around it is still a graph you wrote.

Losing a run is unacceptable

Sandcastle is not a durable execution engine. If the process dies mid-run, the run dies with it. When a workflow moves money or provisions infrastructure and must survive a crash exactly once, that is Temporal's job, not this one — and not LangGraph's either.

Your team wants to stay in Python

Some teams simply prefer their orchestration in the same language and repository as everything else, with the full expressive power that gives them. That is a legitimate preference and no comparison table overturns it.

You need OSI-approved open source

LangGraph is MIT. Sandcastle is BSL 1.1 — source-available, free to read, modify and self-host, but production use needs a licence. If your policy requires an OSI licence today, that is a hard stop and no feature closes it.

04 / Running both

The realistic answer is usually not a migration.

Most teams that end up here do not rewrite the agent. They wrap it: keep the graph that works, and put the schedule, the budget, the record and the retries outside it. 

steps:
  - id: fetch_tickets
    type: http                      # deterministic, $0
    url: "{input.helpdesk_url}/api/tickets?since={input.since}"

  - id: triage
    type: http                      # your existing LangGraph service
    url: "http://langgraph-svc:8000/invoke"
    depends_on: [fetch_tickets]
    body:
      tickets: "{steps.fetch_tickets.output}"
    context_strategy: prune         # shrink an over-budget payload, keep the ending
    output_max_tokens: 4000
    retry:
      max_attempts: 3

  - id: summarise
    type: llm
    model: claude/sonnet-5
    depends_on: [triage]
    prompt: "Write the shift handover from: {steps.triage.output}"

budget_limit_usd: 5.00            # the run stops here, whatever happens

The agent keeps doing what it is good at. What changed is that the run has a ceiling, a retry that resumes rather than restarts, and a row in your own database saying what it cost. If that is the gap you have, this is a smaller change than it looks.

05 / Straight answers

Questions people actually ask.

Is Sandcastle a drop-in replacement for LangGraph?

No, and treating it as one leads to a bad migration. LangGraph models an agent deciding its own next move; Sandcastle models a workflow whose shape you wrote down. If your graph's branching is genuinely dynamic, that logic belongs in an agent — either LangGraph behind an http step, or Sandcastle's own agent step.

Do I have to give up LangSmith?

Not unless you want to. Sandcastle records its own runs — every step, its tokens, its cost, its output — in your database, so for steps it runs you already have the trail. Where it calls a LangGraph service, that service traces to LangSmith exactly as before. Teams usually keep both for a while and then notice they stopped opening one of them.

What happens if the process dies mid-run?

The run fails and is recorded as failed. Sandcastle is not a durable execution engine and does not pretend to be: there is no crash-consistent resume from the exact step. Completed steps are persisted, so a re-run is not a blank start, but if exactly-once survival is a requirement then Temporal is the honest answer.

Can I run it entirely in the EU?

Yes — that is the design premise, not a deployment option. It self-hosts, runs local models through Ollama or oMLX at zero marginal cost, and keeps the run record in your own Postgres. Nothing phones home. The EU AI Act page sets out what that does and does not mean legally.

How mature is this compared with LangGraph?

Far less. LangGraph has a large team, a large community and years behind it. Sandcastle is five months old with one main author. If you need the reassurance of a big ecosystem, that gap is real and you should weigh it. What you get in exchange is a smaller surface: one YAML file, one binary, no control plane you do not own.
